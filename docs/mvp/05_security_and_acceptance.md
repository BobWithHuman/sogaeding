## SPEC-3 당시 문서·준비 기록 (역사 참조)

# MVP 보안 요구사항과 수용시험

작성일: 2026-10-13, Asia/Seoul. 버전: MVP-SPEC-3. 상태: **구현 전 설계 초안 / 모든 시험 미실행**. 이 문서의 P0와 통과 기준은 팀 내부 기준이며 주최 측의 추가 의무나 공식 합격 기준이 아니다. 기술·인터페이스의 최종 선택은 같은 폴더의 요구사항·명세서를 따른다.

## 1. 오늘 증명할 최소 보호 범위

오늘 MVP는 **인증된 사용자 작업 → Codex CLI → 외부 이슈 읽기 → 도구 호출 후보 → 판정 → 실제 executor 실행 또는 거부 → 이력 조회**의 한 경로를 구현한다. 초기 기술 기본안은 Python 3.12, Docker Compose의 FastAPI 제어/PDP·SQLite 서비스와 별도 MCP gateway 서비스, 간단한 HTML 이력 화면이다. MCP gateway 안에 DemoExecutor를 비공개 객체로 두고 backend 실행용 공개 HTTP 포트는 만들지 않는다. 사용자 인증, gateway 서비스 인증, 에이전트 세션 인증을 분리한다. 세션은 실제 MCP 인증 문맥에서 얻으며 에이전트 본문의 세션 주장을 사용하지 않는다.

지원 도구는 `get_issue(issue_id)`, `read_workspace_file(file_id)`, `post_issue_comment(issue_id, body)` 세 개다. `file_id`는 등록된 fixture에 매핑하며 임의 경로를 받지 않는다. 공개 README fixture는 허용하고 가짜 비밀 fixture는 항상 거부한다. 실제 외부 저장소·메일·공용 인터넷에 부작용을 일으키지 않는 모의 executor를 사용한다. 게시·파일 읽기는 실제 모의 저장소의 상태를 바꾸거나 읽게 만들어 단순 UI 메시지와 실행 효과를 구별한다. 별도 gateway effects DB에는 `(session_id, call_id)` 유일성 제약을 적용해 중복 게시를 관측하고 막는다.

P0의 핵심은 출처와 사용자 위임을 따로 기록하고, 외부 문서가 사용자 권한을 늘리지 못하도록 하는 것이다. 외부값의 사용 자체는 공격이 아니다. 예를 들어 사용자가 이슈 요약을 요청했다면 그 이슈의 제목·본문을 읽어 요약에 쓰는 것은 허용한다. 사용자가 요약을 요청했는데 외부 본문이 추가 댓글 작성이나 비밀 파일 읽기를 지시했다면 해당 추가 행동에 권한이 없다.

초기 결과를 “모든 에이전트 행동 보호”, “인과관계 증명”, “IPI 90% 차단 달성”으로 설명하지 않는다. 지원된 경로의 실행 전 권한 통제, 출처 관측, 확인 흐름, 감사 증거가 오늘의 검증 대상이다. 기존 기획서의 정량 목표는 별도 실제 모델 평가 뒤에 판정한다.

초기 MVP는 로컬의 신뢰된 사용자가 세션을 만드는 모드다. **“다중 사용자 계정 서비스 완성”으로 표시하지 않고**, 사용자/서비스/에이전트 인증 분리와 서버 생성 세션별 격리를 검증한다. 공개 네트워크 배포에는 별도 인증·인가·보호 전송 설계가 필요하다. 클라이언트가 임의로 보내는 `user_id` 또는 `session_id` 문자열을 권한 근거로 믿는 구현은 로컬 모드에서도 허용하지 않는다. 브라우저 사용자 자격증명과 gateway 서비스 자격증명이 에이전트에게 전달되어서는 안 된다.

LIVE Codex CLI는 호스트의 전용 CODEX_HOME·가짜 연구 workspace에서 실행한다. 일반 개발 Codex 설정·프로젝트 `.env`·Control/Gateway DB를 읽을 수 있는 연구 workspace를 만들지 않는다. Codex의 내장 셸/파일 도구와 별도 MCP 서버가 자동으로 PDP를 경유하는 것은 아니므로 본 제품의 보호 범위에 포함하지 않는다. 연구 환경에서 불필요한 도구·웹 검색을 비활성화하고 sandbox를 제한하는 설정은 노출을 줄이는 별도 조치이며, 그 설정 자체를 Gateway의 집행 증거로 쓰지 않는다. sandbox에 네트워크 예외가 필요하면 보호 MCP 주소에 한정하고 전체 네트워크를 허용했다고 표시하지 않는다.

구체적인 첫 정책은 `SUMMARIZE_ISSUE`에서 게시를 hard DENY, `POST_COMMENT`에서 지정 이슈와 사람이 제공한 정확한 본문은 ALLOW, 같은 지정 이슈의 다른 본문은 CONFIRM이다. 신뢰된 사용자의 독립된 승인 뒤에도 실행 직전 PDP 재검사와 원자적 단회 소비를 거친다. 지정 이슈 밖 게시와 가짜 비밀 읽기는 승인으로 허용할 수 없다. 판정 상태와 실행 상태 `NOT_STARTED / RESERVED / SUCCEEDED / FAILED / UNKNOWN`은 별도 필드로 유지한다. 승인 뒤 post_issue_comment의 resume_call_id로 같은 호출을 재개한다(03의 계약).

`content_sha256`은 gateway가 수신한 원래 UTF-8 snapshot의 digest로 계산하되, DB에 저장하는 excerpt·매칭 데이터·UI 내용은 마스킹과 길이 제한을 적용한다. 전체 raw snapshot은 요청 처리 범위의 메모리에서만 사용하고 영구 저장하지 않는 것을 기본안으로 한다. 가짜 비밀 sentinel이 공개 이슈 본문에 섞이는 경우에도 에이전트 반환·로그·UI 전에 마스킹한다. 마스킹 범위 밖의 모든 종류의 민감정보까지 완벽히 제거한다고 주장하지 않는다.

실행 0은 API 응답 코드만으로 판단하지 않는다. 판정과 분리된 executor의 호출/읽기/쓰기 기록, 모의 수신함 또는 게시 저장소의 변화, 가짜 비밀의 흐름을 확인한다. 각 case별로 기본 읽기 호출은 허용될 수 있으므로 “모든 도구 호출 0”과 “금지된 행동 실행 0”을 구별한다.

토큰 미노출의 예외는 인증된 사용자에게 새 agent_session_token을 한 번 전달하는 세션 발급 응답뿐이다. 토큰은 이후 조회·공개/비권한 응답·URL·이력에 나타나지 않는다. 실제 LLM API키는 어떤 업무 응답에도 반환하지 않는다.

비공개 executor는 애플리케이션의 노출 인터페이스를 제한하는 방식이다. 같은 OS 계정의 공격자가 임의 Python 코드를 실행하거나 gateway DB를 직접 수정하는 상황을 격리하는 보장은 아니다. AT-04가 통과해도 호스트 전체 shell/file/네트워크 행동 보호로 확대해서 설명하지 않는다.

승인·결정 만료 시간과 입력 크기 한도는 명세서/설정에서 먼저 확정해야 경계값 시험이 가능하다. 수용시험에서 임의 수치를 공식 요구로 만들지 않는다.

## 5. replay와 실제 LLM 시험 분리

| 시험 모드 | 입력 후보 생성 | 증명할 수 있는 것 | 추가로 필요한 것 |
|---|---|---|---|
| `REPLAY` | 고정 fixture가 정해진 tool 후보·요약을 제출 | 계약·권한·출처·판정/실행 연결·승인/장애 처리의 재현성 | 실제 모델의 공격 반응·정상 과업 수행 검증 |
| `LIVE` | 고정 버전의 실제 모델/에이전트가 외부 이슈를 읽어 후보 생성 | 지정 모델·도구·입력 범위에서 위험 행동 통제와 정상 완료 | 반복 측정, 별도 평가셋, 실패 사례와 모델 조건 기록 |

LIVE의 에이전트는 Codex CLI이고 제공자는 OpenAI다. 실제 CLI 버전·모델 ID·API 인증 성공·MCP 연결 성공을 결과마다 기록한다. CLI 설치 확인과 API 키 보유만으로 LIVE PASS를 쓰지 않는다. PDP의 OpenAI 의미 판정 judge는 P1·기본 OFF이며 Codex 모델 호출과 별도 구성이다.

오늘 REPLAY 먼저 성공해도 LIVE는 실제 실행 전까지 `NOT_RUN`으로 유지한다. 실제 모델이 원래 공격 호출을 생성하지 않았다면 “엔진이 공격을 차단했다”로 집계하지 않는다. 판정 엔진 앞까지 동일한 위험 후보가 도달한 대조군과 보호군을 구분한다. LIVE 데모를 추가할 때는 가짜 비밀과 통제된 모의 수신기만 사용한다.

후속 live 평가는 최소한 모델 제공자/정확한 model ID, 실행 시각, 설정, 프롬프트/fixture 버전, 반복 수, 보호 유무, 후보 호출, 실제 부작용, 정상 작업 완료, 확인 대기, 실패를 남긴다. replay와 live 수치를 합치거나 고정 시나리오의 통과율을 일반적인 IPI 차단률로 발표하지 않는다.

## 6. 결과 장부와 오늘 완료 기준

각 실행 결과의 최소 필드는 `run_id, mode, case_id, fixture_version, build_version, policy_version, session_ref, expected_decision, actual_decision, tool, arguments_digest, decision_id, executor_invocations, actual_effects, final_task_status, elapsed_ms, evidence_path, result`다. `result`는 `NOT_RUN / PASS / FAIL / BLOCKED` 중 하나다. 원문 비밀·토큰은 저장하지 않는다. 증거 파일이 비밀을 포함한다면 마스킹된 결과와 접근 제한된 원본을 구분하며 제출에는 가짜 비밀만 사용한다.

오늘 P0 보안 완료는 위 시험이 실제 실행된 결과로 판정한다. 실패를 숨기거나 예정된 수치를 달성 결과로 옮기지 않는다. 오늘 기능 개발이 먼저 완료됐더라도 승인 replay·세션 혼합·판정 우회·비밀 읽기·판정 실패 후 실행이 남아 있으면 보안 MVP는 미완료로 기록한다. UI 표현 개선·다중 에이전트·완전한 로그 변조 탐지·대규모 성능 평가·외부 공급망 검사 자동화는 후속 작업으로 추적하되, 외부 서비스 공개 조건과 별도로 관리한다.
