# ADR-S01: 인증·중요정보 경로의 보호 전송

상태: **ACCEPTED — 설계 판단 / 구현 NOT_STARTED**. 결정일 2026-10-13(KST). 판단 근거는 사용자가 R1/G1/G2/G3/G4 가이드 준수를 필수 개발 기준으로 지정한 현재 지시다.

## 배경과 근거

현재 MVP-SPEC-2는 호스트 `http://127.0.0.1:8000`, MCP `http://127.0.0.1:8001/mcp`, 내부 `http://control:8000`을 사용하도록 작성됐다. 에이전트 세션 토큰, 사용자 토큰, Gateway 서비스 토큰과 업무 데이터를 이 경로로 보낸다. 앱 소스는 아직 없으므로 제품에서 이 경로가 안전하다는 실행 증거도 없다.

G3 PDF/인쇄 p.510의 SR2-7은 중요정보의 암호화 저장, SR2-8은 인증정보 전송 암호화를 다룬다. 관련 설계 본문은 SR2-7 p.153 이후, SR2-8 p.159 이후다. 원 예선 P1 p.5~6은 mTLS·민감정보 보호를 계획했다. loopback 바인딩과 Compose 내부망은 노출을 줄이지만 보호 전송 요구를 충족했다는 단독 증거로 사용하지 않는다. 정확한 적용과 저장 요건은 [준수표](../guide_compliance.md)에서 경로별 검토한다.

## 결정

1. 사용자/런처→Control, Codex→MCP Gateway, Gateway→Control의 **인증정보를 담은 TCP 경로는 TLS와 서버 인증서 검증을 필수로 구현**한다. 서비스 간 mTLS를 우선 구현 방향으로 두어 예선의 계획을 구체화한다. 서로 다른 프로토콜/구조로 동등 보호를 제안하면 구현 전에 별도 근거·관리 판단을 남긴다.
2. 인증서 만료·잘못된 신뢰기관·호스트 불일치·필요한 클라이언트 인증 실패는 fail-closed다. `verify=False`, 검증 콜백 항상 성공, HTTP fallback, 키/토큰을 querystring에 넣는 회피는 허용하지 않는다.
3. 앱 전용 인증서/신뢰 설정을 사용한다. 개인키를 Git·이미지·프롬프트·로그에 넣지 않는다. 호스트 전체 신뢰 저장소·전역 Codex 설정을 임의 변경하지 않는다. 자격증명 전달·인증서 수명·파일 권한·폐기/재발급 절차를 기록한다.
4. Codex의 실제 버전과 설치된 MCP/HTTPX/서버 API에서 CA·mTLS·시간 제한을 어떻게 전달하는지 **지원 스파이크로 확인**한다. 확인하지 않은 설정 키나 환경변수가 동작한다고 쓰지 않는다. 로컬 CA 지원이 OpenAI의 정상 HTTPS 검증을 깨뜨리지 않는지도 확인한다.
5. 원문 비저장·마스킹·토큰 해시·접근권한은 계속 적용한다. 저장되는 데이터 중 중요정보를 식별해 보호 저장을 구현하고 시험한다. 비밀을 저장하지 않도록 설계한 경로와 중요한 사용자 데이터를 저장하는 경로를 구별한다. 해시를 암호화 저장과 동일시하지 않는다.

## T-S01의 범위와 의존성

T-S01은 SPEC-3 전송 기준·기계 설정 동기화, 앱 전용 인증서/신뢰 구성, 라이브러리 지원 확인, 가짜 TLS endpoint에서 검증 성공/실패·개인키 미노출을 확인하는 **준비 작업**이다. 제품 서비스/인증이 구현되기 전에 전체 제품 health를 요구하지 않는다.

세션 모델·DB·순수 정책의 네트워크 비노출 단위 구현은 T-S01과 병렬 가능하다. 실제 인증 TCP endpoint를 열거나 세션 토큰을 보내는 제품 통합은 준비된 보호 전송 경로를 사용한다. T-01/T-04 완료 시 실제 Control/MCP/internal 경로에서 다시 검증한다. 이 분리로 TLS 준비가 제품 auth를 기다리고 제품 auth가 TLS 전체 시험을 기다리는 순환을 만들지 않는다.

기존 작업 장부의 T-00 DONE은 개발 도구 준비가 끝났다는 의미다. 이번 결정으로 새로운 전송 구현·제품 인증·가이드 준수가 완료되었다는 뜻으로 확대하지 않는다.

## 사전 위임한 개정과 유지할 의미

WP-MVP-01의 T-S01 담당은 `docs/mvp/00~07`, `docs/mvp/contracts/`, `compose.yaml`, Docker/필요 의존성·실행 scripts·Codex profile을 전송 기준에 맞춰 동기화할 수 있다. 문서/wire version을 MVP-SPEC-3으로 일관되게 개정하고 변경표·유효 예시·검사도 갱신한다. 정책 `mvp-2026-10-13-v1`, 도구 범위·입력/응답 의미·권한·판정·승인·실행 상태 전이는 그대로 유지한다. 그 의미의 변화는 추가 관리 결정이 필요하다.

현재 세션은 계획만 작성한다. 해당 files는 아직 SPEC-2이며 실제 설정 변경/인증서 생성/신뢰 설치는 수행하지 않았다. 계약 개정이 끝나면 구현자가 RESULT로 버전·diff·시험을 넘기고 관리 세션이 적용 상태를 확인한다.

## 보충 시험: PL-SEC-TRANSPORT

기존 제품 수용시험 18개와 별개로 다음 실제 제품 검증을 추가한다. 모두 현재 NOT_RUN이며 제품 계약 개정 시 정식 시험표에 연결한다.

- 정확한 CA·호스트·유효 인증서로 세 역할의 정상 인증/도구 호출이 성공한다.
- 잘못된 CA·호스트·만료 인증서와 필요 시 누락/잘못된 클라이언트 인증은 연결/업무를 거부하고 금지 효과 0이다.
- 인증 트래픽의 평문 endpoint/fallback을 사용할 수 없으며 인증정보가 URL·로그·응답·Git·이미지에 남지 않는다.
- 실제 Gateway→Control timeout/검증 실패 때 executor를 실행하지 않는다. 사용자의 승인도 전송 오류를 우회하지 않는다.
- 전용 Codex profile의 CA 전달을 실제 MCP 연결로 확인하며, OpenAI 모델 연결은 별도 LIVE 결과로 확인한다.

TLS fixture 준비 PASS와 실제 제품의 PL-SEC-TRANSPORT PASS는 다르다. 보호 전송/중요정보 보호의 적용 P0가 미완료면 **가이드 준수 core/MVP 완료 선언을 하지 않는다**. 결정적 정책 REPLAY가 부분적으로 동작한 사실은 범위를 표시해 별도로 보고할 수 있다.
