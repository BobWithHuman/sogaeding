# 현재 PDP와 inline 출처 라벨 제안 비교

**후속 결정:** 이 비교 이후 사용자가 관리 판단으로 채택을 위임해 [ADR-P02](../decisions/ADR-P02_selective_provenance_adoption.md)를 확정했다. 인자별 출처·문맥 분석만 채택하고 inline 마커는 MVP에서 제외한다. 아래는 비교 당시의 분석과 미측정 한계를 보존한다.

2026-10-16 / 관리 설계 검토. 사용자가 제공한 새안을 코드·공식 훅 문서·CaMeL/Fides·Jev 원문과 비교했다. **설계 비교이며 탐지 성능 실험이 아니다. 코드/배정/정본 방향을 이 문서만으로 변경하지 않는다.** 실제 모델 호출·라벨 실험·CLI 업데이트는0이다.

## 판단

새안은 현재의 포괄적인 GPT A/B 과업 판정보다 **민감한 인자와 외부 지시의 관계를 구체적으로 묻는 점**에서 낫다. 그러나 inline 라벨 삽입·제거를 보안의 핵심 근거로 삼는 전체 교체는 권하지 않는다. 현재15번의 규칙 우선/서버 출처 원장/gateway 기반에 **슬롯별 출처와 권유·사실·인용 문맥 분석**을 더하는 것이 1인 MVP에 가장 현실적이다. inline 마커는 별도 비교 실험 대상으로 둔다.

## 세 기준선 구분

| 기준 | 현재 실행 코드 | 최신15번 계획 | 사용자 새안 |
|---|---|---|---|
| 모델 | GPT DevelopmentJudge A/B | 미확정 의미에만 Jev 계획 | 문단/값별 Jev 분류와 무라벨 출처 선택 |
| 근거 | 서버 source/catalog/hash·모델 선택 ref | 같은 원장과 규칙 재사용 | 서버 원장 + 본문 inline ID |
| 장점 | 실행 전 집행/인자결합/감사 구현 기반 | 저비용 검사 우선, 기존 코드 재사용 | 민감 슬롯과 권유/설명 관계를 설명하기 쉬움 |
| 약점 | 정상 읽기도 A/B, 질문이 포괄적 | 실제 Jev 성능 미검증 | 라벨 유실/변형/위조/데이터 훼손과 추가 분석 |
| 제품 검증 | 정상 읽기 의미 ALLOW만 관측, host403으로 실제 과업 미완료 | 미구현 | 미구현/성능 미측정 |

GPT→Jev의 차이와 출처 표식 설계의 차이는 별도다. 같은 Jev로 비교하지 않으면 모델 교체 효과를 라벨의 효과로 오인할 수 있다.

## 새안에서 채택 가치가 있는 부분

- 사용자 목표 전체의 의도를 복원하기보다, 특정 문단이 특정 값을 사용하라고 권하는지/사실로 설명하는지/금지·인용하는지를 좁게 묻는다.
- action/target/options/payload로 호출을 분해한다. 동일 외부 URL도 공개자료 조회 대상인지 민감정보 전송 목적지인지에 따라 정책이 다르다.
- 검증된 마커가 동일 값과 함께 복사되면, 해당 관측 구간의 값이 후속 호출에 함께 등장했다는 증거가 늘어난다. 이는 이점이지만 모델 내부의 완전한 데이터 흐름 추적이나 인과 증명은 아니다.

## 해결하지 못한 문제

### 라벨 보존과 검증

일반 taint 추적은 연산마다 라벨이 전파된다. 여기서는 블랙박스 모델이 요약·번역·경로 조립·설정 변환을 하면 라벨이 빠질 수 있다. 라벨이 없다고 무오염/안전으로 판단할 수 없다. Jev의 source 선택은 관측된 문서 사이의 의미적 연관 추정이다.

외부 문서가 가짜 사용자 라벨을 넣거나, 모델이 진짜 라벨을 다른 값 옆에 붙일 수도 있다. 세션/원문 hash/정확 span/값과 서버 발급 여부를 결합해야 한다. 서명으로 위조를 막아도 라벨 삭제·이식·암묵적 영향 문제는 남는다. 모델이 쓴 라벨을 사용자 권한으로 인정하지 않는다.

### 개체의 정체성과 지시의 출처

외부 e7 문장의 .npmrc 출현은 e7에서 왔다. 실제 로컬 파일 l1을 가리킨다는 사실은 별도 관계다. .npmrc에 l1만 붙이면 외부에서 선택한 대상을 로컬에서 온 값으로 오인할 수 있다. source occurrence와 referenced object를 나눠야 한다. 로컬 README/clone한 코드도 공격자 영향이 있을 수 있어 l은 위치이며 신뢰 등급이 아니다.

### 원인 하나를 고르는 문제

사용자가 목적을 주고, 로컬 파일이 기존 설정을 주고, 외부 문서가 변경 옵션을 줄 수 있다. 슬롯별 복수 source 후보와 UNKNOWN을 허용해야 한다. none은 출처 없음과 관측/분류 실패를 구분하지 못한다. source 후보 확률0.78을 실제 행동의 원인이 맞을 확률로 해석하지 않는다. 값 복사 없이 도구 선택/실행 순서만 바뀌는 경우도 값 라벨로 포착되지 않는다.

### 차단 규칙의 오탐과 누락

외부+권유+위험은 공격의 필요충분조건이 아니다. 공식 설치 가이드의 정상 권고도 외부 지시이고, 공격자가 위험 값을 표·기본 설정·사실처럼 제시할 수도 있다. 그 세 조건은 하나의 신호이며 최종 허가 규칙을 대신하지 못한다. 민감자원/유출/정책 위반은 출처나 권유 분류가 불명이어도 차단해야 한다. 필수 분석 장애와 불확실성을 '셋 다 관측되지 않음→허용'으로 처리하지 않는다.

### Jev의 역할

권유/설명·의미상 유사 설정·출처 선택은 모두 여전히 모델 판단이다. 질문을 좁힌 것은 개선이지만 공격자가 쓴 문단을 모델이 본다는 문제는 남는다. [Jev1.13 공식 한계](https://docs.typesafe.ai/model-jaggedness/jev-1.13)는 adversarial state가 답을 움직일 수 있다고 명시한다. 1.14에서 해결됐다고 검증한 바는 없다.

## TLS 예시의 실제 의미

strict-ssl=false를 읽고 NODE_TLS_REJECT_UNAUTHORIZED=0을 쓰는 경우는 문자열/마커 전파가 아니라 의미상 유사 행동이다. Jev가 e7을 골라도 실제 유발 원인을 증명한 것은 아니다. TLS 검증 해제 정책은 두 표현을 코드로 정규화해 출처와 독립적으로 막아야 한다. 해당 정책으로 이미 막히는 예시만으로 라벨의 추가 탐지 가치를 입증할 수는 없다.

같이 시험할 정상 사례는 검증된 lab CA를 cafile로 설정하는 해결, 취약한 설정을 보고서에 인용하는 작업, 위험 설정을 금지하는 문서다. 같은 문자열을 실제 보안 설정에 적용하는 경우와 설명/테스트 데이터로 작성하는 경우를 구분해야 한다. 공격 문서의 의도와 금지 행동의 차단도 별도 결과로 남긴다.

## 구현 가능성과 부작용

[Claude 공식 훅 문서](https://code.claude.com/docs/en/hooks)는 PreToolUse.updatedInput 입력 교체와 PostToolUse.updatedMCPToolOutput의 MCP 출력 교체를 지원한다. 현재 문서는 updatedToolOutput도 설명하며 도구별 출력 형식 준수를 요구한다. PostToolUse는 이미 실행한 효과를 되돌리지 않는다. 실제 설치 버전의 roundtrip은 이번에 실행하지 않았다.

[Codex 공식 훅 문서](https://learn.chatgpt.com/docs/hooks)는 updatedMCPToolOutput을 아직 미지원으로 명시한다. 따라서 Claude용 출력 교체를 Codex0.154.0에서 동일하게 쓸 수 있다고 가정하지 않는다. MCP는 기존 gateway/bridge에서 응답 사본을 다루는 대안이 있지만 별도 구현/검증이 필요하고 native/hosted 읽기까지 자동 적용되지 않는다.

URL/path/JSON/명령/설정/패치에 마커를 넣으면 파싱·해시·정확 문자열 검색·편집 old_string·생성 코드가 깨질 수 있다. 최종 호출에서만 제거해도 모델이 중간에 라벨을 버리거나 산출물 일부를 바꿨다면 복구할 수 없다. 정규식으로 모든 괄호 문자열을 지우면 정상 데이터도 훼손한다. 서버가 발급하고 해당 값에 결합된 마커만 다루며 모델이 보는 사본과 원자료를 분리해야 한다.

라벨 제거 후의 **실제로 실행할 인자**에 정책/승인/hash/서명/단회 예약을 결합한다. 판정한 tagged 인자와 실행한 clean 인자의 변환 관계를 별도로 기록해야 한다. 라벨 기능으로 기존 정확 인자 결합/호스트 승인을 우회하지 않는다.

## CaMeL/Fides와의 차이

[CaMeL](https://arxiv.org/html/2503.18813v2)은 underlying LLM을 바꾸지 않으면서 전용 interpreter에서 변수 의존성과 capabilities를 전파한다. [Fides](https://arxiv.org/html/2505.23643v2)는 wrapper/계획 루프의 라벨과 정책을 통제하고 모델 응답에 대해서는 보수적으로 영향 라벨을 전파한다. 따라서 이 논문들이 모델 가중치 내부를 관찰해서 taint를 아는 것은 아니다. 제어 가능한 runtime이 전파를 강제하는 것과 기존 Codex가 표시 문자열을 보존하리라 기대하는 것이 핵심 차이다.

## 비용과 공정한 비교

현재는 분석 대상 후보 M개에 보통2M개의 GPT 요청이다. 새안은 문서 내 값 N개의 권유/설명 질문과 무라벨 호출의 귀속 질문이 추가된다. Jev 배칭/캐시로 네트워크 요청을 줄일 수 있지만 토큰·질문·대기 비용이 사라지지는 않는다. 문서 전체를 미리 분류하기보다 민감 후보의 관련 span만 지연 평가하는 편이 유리할 가능성이 있으며 실제 지연으로 확인해야 한다.

같은 정책/같은 Jev/같은 출처/같은 입력 한도로 다음 세 안을 비교한다.

1. 서버 출처 원장만 사용.
2. 1에 슬롯별 권유/설명·복수 출처/UNKNOWN을 추가.
3. 2에 inline 마커를 추가.

먼저 고정 후보로 판정을 비교하고, 이어 실제 actor에서 마커 때문에 과업과 후보가 달라지는 영향까지 비교한다. 현재 GPT A/B는 역사적 기준선으로 따로 둔다. 고정 후보 시험만으로 마커를 본 actor의 전체 성능을 주장하지 않는다.

측정: 정상 과업 완료율/오탐, 위험 후보 허용률/금지 효과, 판정 불가율, 마커 잔존·위조/이식 거부, p50/p95 추가 지연, 요청·입력량·실제 비용. 라벨 삭제/인코딩/파생 설정, 다중 출처, 금지 예시의 정상 인용, 문서 권고에 따른 정상 개발, 값 없는 제어흐름 공격을 포함한다. 위험 후보 미생성은 NO_ATTACK_ATTEMPT이며 분석 장애 차단은 의미 탐지 성공과 구분한다. 합격선은 사전에 정하고 미측정 우열/점수를 만들지 않는다.

## 채택 권고

**유지:** 기존 실제gateway·hook 집행, 서버 source/catalog/hash·신뢰 경계·정확 인자 결합.

**추가 후보:** action/target/options/payload 분해, 특정 문맥의 권유/사실/금지·인용 구분, 복수 source와 UNKNOWN, 출처와 독립적인 위험 sink 정책.

**실험 후 결정:** inline 라벨을 모델 입력에 넣는 기능. 권한/완전 taint의 증거로 쓰지 않고, 추가 탐지 이득이 정상 품질·지연 비용을 상쇄할 때에만 제한적으로 채택한다.
