**오늘 MVP 개발 완료는 6종 제출물 완성이 아니다.** 오늘 확보한 실행 이력·fixture·진단 baseline·화면 기록은 제출물의 재료다. 제품 구현 완료, 제품 자체 보안 검토 완료, 제출물 제작 완료, 실제 제출 완료를 서로 다른 게이트로 판정한다.

## 3. 기획서 제2항과 F1~F5 연결

[첨부 보안 기준 실행표](05_contest_security_criteria.md)의 IMG-09와 대조해 제2항의 각 기능에 아래 연결을 넣는다. 기획과 다른 구현 선택을 숨기지 말고 적용한 이유와 이행 결과를 설명한다.

| 기능 | 제2항에서 설명할 실제 구현 | 연결할 증거·남은 한계 |
|---|---|---|
| F1 출처 표식 | 인증된 사용자 요청과 Gateway가 읽은 외부·workspace 데이터의 등급 분리, 원문 digest·마스킹 발췌, 본문 내 위조 라벨의 비효력 | 발급·저장 코드, 출처 위조·비밀 비노출 시험. 외부 문자열 일치는 관측임을 명시 |
| F2 행동 이력 | session→source→call→decision→approval→reservation→execution·receipt 연결 | 동일 run의 안전한 이력·effects 비교, 세션 격리 시험. 원 기획 PostgreSQL/OTel 등 실제 채택·미채택 구분 |
| F3 판정 | ALLOW/DENY/CONFIRM의 결정적 권한 정책, 읽기 자원 검사, 인자·정책 결합, 출처 대조의 용도 | 같은 도구·인자의 사용자 요청/외부 추가 지시 대비. 의미 judge OFF면 "3단계 전부 구현"으로 쓰지 않음 |
| F4 집행·재개 | private executor 앞 검사·원자 예약, 정확한 승인 단회 소비, DENY 비승격, UNKNOWN 자동 재시도 금지 | 실행 0/1·동시성·승인 replay·보고 손실 회귀. 원 기획의 반복 공격 후 최종 확인과 실제 hard DENY 정책 차이를 명시 |
| F5 대시보드 | 세션 타임라인·출처·판정 이유·승인·실제 실행 상태, 안전한 출력 | UI 캡처와 조회 API 권한·HTML/민감정보 시험. 단순 타임라인이면 전체 그래프·오탐 분석 완성으로 쓰지 않음 |

구조적 설계는 설계명 나열이 아니라 **예방하려는 약점 → 신뢰 경계·규칙 → 코드 위치 → 실패·공격 조건의 시험 → 실제 결과**로 설명한다. mTLS·해시 체인·agentgateway 연동 같은 원 기획 약속은 실제 구현·시험한 범위만 완료로 표시하고 나머지는 변경 사유·후속 계획으로 남긴다.

P1 p.8의 **차단률 90% 이상·과차단률 10% 이하·판정 50ms 이하**는 원 기획의 목표다. 실제 결과와 조건이 확보되기 전에는 성과표·포스터·영상에 달성 수치로 넣지 않는다. 현재 제품 수용시험 수·ID의 정본은 `docs/mvp/05_security_and_acceptance.md`이며 변경 시 제출문서의 복사된 개수도 함께 대조한다.

C1 p.26의 우선순위는 **빌드라인 당 소스코드 보안약점의 수 → 보안약점 조치율 → 구조적 설계**다. "빌드라인" 정의·분모·산식·오탐 처리·분석 대상은 미확정이다. LOC를 늘리거나 불리한 파일을 숨겨 점수를 유리하게 만들지 않는다. 내부 보고는 공식 점수로 환산하지 않고 아래 형태로 남긴다.

- 진단 ID, guide/CWE 항목, 대상 파일·함수·버전, 검사 도구·버전·명령·시간.
- 발견 원본·재현 조건·영향, 실제 약점/오탐/적용 제외 판정과 검토 근거·검토자.
- 수정 전 상태·원인·수정 코드/commit, 회귀 시험·수정 후 원시 결과, 미해결 위험·사유.
- 같은 스캔 범위와 조건으로 비교했는지, 범위가 바뀌었다면 비교 한계.

원본 발견을 수정 후 결과로 덮어쓰지 않는다. 적용 제외는 단순 "Python이라 없음"이 아니라 실제 기능·의존성·native 코드·경계와 근거를 확인한다. 가이드 준수 주장은 [03_guide_compliance.md](03_guide_compliance.md)의 적용표와 실제 검증 결과를 따른다.

안전한 제출 폴더의 내부 권고는 `submission/R2/v1.0/`다. 파일명을 짧고 일관되게 쓰고 공식 규칙이 없으면 ASCII 이름을 사용하되 문서 안에는 한글 팀명·프로젝트명을 명시한다. `final_final`이나 변경되는 `latest`만으로 정본을 구분하지 않는다. 원본 PDF 가이드 전체, 다운로드 폴더, `.git`, 개발용 가상환경·캐시, 개인 `.codex` 설정·로그·auth, 실제 서비스 DB·키 파일을 무조건 압축하지 않는다. 라이선스와 제출 요구에 맞춘 필요한 코드·의존성 정보·안전한 fixture·증거만 포함한다.

권고 manifest 필드: `artifact_id, kind, relative_path, bytes, sha256, release_id, source_commit, created_at, reviewed_by, evidence_index`다. manifest 자체의 SHA-256은 별도 내부 기록으로 남긴다. manifest가 가리키는 파일을 수정하면 같은 manifest를 그대로 쓰지 않고 새 버전·해시로 교체한다. 원격 서비스가 해시를 제공하지 않으면 업로드본을 다시 내려받아 로컬 동결본과 비교하거나 가능한 대조 방법·한계를 기록한다. 제출 링크가 있다는 사실만으로 읽기 권한·파일 온전함이 확인된 것은 아니다.
