## 2. 초기 상태와 판정 규칙

현재 저장소에는 명세·계약·개발 하네스·Docker 준비 증거가 있고 제품 소스는 준비 안내 단계다. 하네스의 계약·런처 검사는 제품 수용시험과 다르다. 이 계획 작성 시 제품 코드 전체의 수동 검토·49개 적용성 확정·20개 설계 진단·실제 MCP 수용시험·LIVE·최종 이미지 SBOM을 다시 실행하지 않았다. 기존 준비 결과는 범위·시점이 명시된 준비 증거로만 사용한다.

| 축 | 가능한 값 | 판정 규칙 |
|---|---|---|
| 적용성 | 미점검 / 적용 / 비적용 후보 / 비적용 확정 | 아래 표의 초기 제품 상태는 모두 미점검. 검토 계획에 적힌 적용 예상·비적용 후보는 코드 관찰 결과가 아님 |
| 작업 | TODO / IN_PROGRESS / BLOCKED / DONE | DONE에는 실제 변경 파일·검토자·명령·증거가 필요 |
| 시험 | NOT_RUN / PASS / FAIL / BLOCKED | 실제 명세의 경로·효과로 시험해야 PASS. mock 판정·UI 색·하네스 PASS로 제품 PASS를 대신할 수 없음 |
| 진단 발견 | 미분류 / 정탐 / 오탐 / 수정 중 / 재진단 제거 확인 | 오탐·비적용은 이유·입력 출처·sink 부재/방어경로·독립 검토 근거를 남김 |

비적용 확정에 필요한 증거는 대상 파일/서비스 범위, 코드·의존성 검색, 해당 기능/API/sink 부재, 대체 경로와 네이티브 경계 검토, 검토자·날짜다. 기능 또는 의존성이 새로 들어오면 해당 행을 다시 미점검으로 돌린다. Python 언어 이름이나 로컬 실행이라는 이유만으로 비적용 확정하지 않는다.

**지금 해소해야 할 명세 공백:** 기존 MVP-SPEC-2의 HTTP loopback와 Docker 내부 네트워크 격리는 노출을 줄이지만 G3 SR2-8의 인증정보 암호화 전송을 충족했다는 증거가 아니다. 관리 세션은 [ADR-S01](C:/sogaeding/docs/plans/decisions/ADR-S01.md)로 AUTH_TCP_TRANSPORT TLS를 오늘 필수 게이트로 채택한다. 인증정보가 흐르는 host→control, host/Codex→MCP, gateway→control TCP 경로에 TLS와 인증서 검증을 적용하며 gateway→control은 원 기획의 mTLS를 우선 구현한다. 개발 세션은 API/Compose/설정/런처에 있는 HTTP baseline과의 충돌을 개정하고 실제 보호 채널을 확인해야 한다. 기존 문서의 mTLS 후속 작업 표현은 이 결정과 충돌하며 개정 대상이지 인증정보 보호 의무의 면제가 아니다. 동등 보호 방식이 필요하면 별도 ADR에서 위협·전송 기밀성/무결성·상대 인증·실제 시험 근거를 검증해야 한다. SDK/CLI의 프로토콜 지원이 아직 확인되지 않았다는 이유로 보호 의무를 면제하지 않는다. HTTP 상태에서 가짜 fixture로 집행 기능을 검증할 수 있어도 **TLS 게이트가 미완료이면 가이드 준수 MVP 완료·가이드 전체 준수 PASS·실자료 사용·외부 공개 운영 완료는 선언하지 않는다.** 시간 부족은 미준수 통신을 완료로 처리할 이유가 아니다.

중요정보 저장도 마찬가지다. secret fixture를 차단하고 raw 원문을 영구 저장하지 않는 설계, 고엔트로피 bearer의 검증용 digest, 일반 소스 식별 해시를 실제 중요정보 평문 보관과 구분한다. 실제 중요정보를 보관하는 기능이 필요하면 안전한 암호화·키 생명주기·조회권한·보존/폐기를 구현하고 검증한다. 실제 OpenAI API키는 호스트의 허용된 child 환경에만 주입하고 prompt·컨테이너 이미지·증거 파일로 넘기지 않는다.

## 6. Python 코드 작성·검토·진단 흐름

개발 세션은 [with-human-dev](C:/sogaeding/.agents/skills/with-human-dev/SKILL.md)의 작성자/검토자 분리와 [evidence.md](C:/sogaeding/.agents/skills/with-human-dev/references/evidence.md)의 실제 효과 기록을 사용한다. 다음 절차는 모든 기능 묶음에 반복한다.

1. **설계 진단:** 요구 ID·위협·자산·권한·입력·sink·실행효과를 읽고 설계20행/49행 중 관련 항목을 표시한다. 입력 스키마/DB 전이/권한/암호·보존 조건이 빠지면 구현 전에 결정한다.
2. **안전하게 작성:** SQL 바인딩, JSON 엄격 검증, 임의 eval/exec/shell 금지, 등록 fixture, 검증된 난수·암호·TLS, 목적별 최소권한, 불변 action·원자적 소비, 안전한 오류/자원 정리를 코드 공통 경로로 만든다.
3. **1차 진단:** lint와 보안 SAST·secret/SCA를 수행하고 룰셋/버전/제외경로·명령·exit code를 기록한다. 모든 49행은 수동으로도 source→sink→검증/권한→효과를 본다. Bandit/Semgrep 같은 도구 이름이나 lint PASS는 전수 진단의 대체물이 아니다. W/SR별로 실제 적용된 도구 rule ID, 수동 확인 경로, 동적 case ID를 나누어 기록한다. 룰이 없는 항목은 미지원으로 표시하고 수동·실행 검증으로 보완한다. 첫 실행 가능한 제품 버전의 진단 원본과 범위 manifest를 보존한다.
4. **동적 검증:** 실제 MCP 인증→control→reserve→executor→effects/report→UI를 통과시킨다. 정상·공격·권한 위조·동시성·장애·XSS/민감정보·입력 한도를 확인한다. 단위시험과 core/REPLAY/LIVE 시험의 범위를 구분한다. C1 PDF14~15의 실행코드 진단을 위해 가짜 데이터의 로컬 제품에 인증·입력·헤더·인증서·오류 응답 스캐닝과 경계 우회·승인 경쟁 등 모의침투 시나리오를 적용한다. 실행 중 제품의 요청/응답·상태·효과를 관찰해야 하며 SAST, SCA, mock 단위시험 또는 IPI 차단률로 대신하지 않는다.
5. **수정·2차 진단:** 정탐 원인을 공통 통제로 수정하고 같은 공격/정상 회귀시험과 관련 진단을 다시 한다. 수정 전 실패/실제 위험 증거와 수정 후 제거 증거를 모두 남긴다. 이미 취약 동작이 있는 경우 수정 전 기준을 보관하되 검증 목적으로 새 실제 비밀·외부 부작용을 만들지 않는다.
6. **독립 검토·종료:** 검토자는 실제 diff·진단 결과·effects/DB·시험 증거를 읽는다. 오탐·비적용 결론과 남은 약점을 확인하고 관리 세션에 사실/판정/다음 조치를 넘긴다. 필요한 시험이 NOT_RUN이면 준수 PASS를 선언하지 않는다.

1인 개발의 산출물은 작업 인계 폴더 안의 **`SECURITY_DESIGN.md`(보안 요구·위협·외부 인터페이스·통제·표준코딩), `GUIDE_APPLICABILITY.md`(20/49 적용성·정적/수동/동적 진단·원증거 색인), `FINDINGS.jsonl`(발견·판정·수정·재진단 이벤트)** 세 파일로 통합한다. 기존 요구/API 문서를 링크하고 중복 명세를 만들지 않는다. 현재 세 제품 보안 산출물의 작성·실행 상태는 **NOT_STARTED**이며 이 계획의 표를 복사하는 것으로 PASS가 되지 않는다. 구체 필드와 완료 조건은 [대회 기준 대응 계획](05_contest_security_criteria.md)에 있다.

발견 ID와 최초 관찰은 덮어쓰지 않는다. 정탐·오탐·중복·비적용 후보·조치·재진단·재개방을 새 이벤트로 남기고 기준 코드 버전·범위·원증거를 묶는다. 동일 범위의 확정 정탐 중 재진단으로 제거된 수는 내부 조치 추적에만 사용하며 공식 조치율로 단정하지 않는다. C1 PDF26의 “빌드라인” 정의와 공식 산식은 미공개이므로 임의 LOC 분모나 공식 점수를 만들지 않는다. 미진단·도구 실패·미지원 항목은 잔존 0건이 아니다. 원래 결함이 없는 기능에 조치 실적을 만들기 위한 약점을 추가하지 않는다.

가이드 예제 검토 시 이미 알려진 주의점도 넘긴다. G2 PDF21·23(인쇄15·17)의 eval/exec 예제, PDF25~26(인쇄19~20)의 문자 삭제 기반 경로 예제, PDF42·162(인쇄36·156)의 URL/DNS 예제를 제품의 완성 통제로 복제하지 않는다. | 빌드/배포 권한 | secret 없는 검증·최소권한·개발/배포 권한 분리·서명/업데이트 경로 검토 | 설정 diff·저장소 접근·safe default·설치/rollback/패치 절차 | 개발 시작, 제출 전 |

SBOM 최소 근거는 G1 PDF45~47(인쇄35~37)이다. 7개 기본 필드는 공급자명·작성주체(Author Name)·구성요소명·버전·고유 식별자·의존관계·생성시각이다. 표의 한글 “저작권자”를 실제 copyright owner로 기계 대응하지 말고 본문 정의인 SBOM 생성주체로 기록한다. 새 build/release마다 생성, 하위 의존관계 포함, 알려진 미확정 사항 표시, 적절한 제공·접근제어·오류/누락 처리도 함께 적용한다.

G1 PDF62~68(인쇄52~58)의 실증은 source/바이너리·도구별 차이와 명칭/라이선스 누락·중복을 보여준다. 따라서 생성된 JSON 한 개만으로 완료하지 않고 설치 구성과 비교한다. G1 PDF48~50(인쇄38~40)은 CVE/KEV·실제 영향 기반의 취약점 관리, PDF51~53(인쇄41~43)은 라이선스 확인에 사용할 근거다. 최종 판단에 쓰는 새 CVE·암호/API·라이선스 조건은 개발 당시 공식 출처와 실제 package metadata에서 확인한다.

VEX는 R1 PDF25(인쇄021)의 “알려진 구성요소 취약점의 악용 가능성 여부 전달”과 G1 PDF58(인쇄48)의 향후 교환 체계에서 가져온 개념이다. **모든 build에 무조건 빈 VEX 파일을 제출해야 한다는 대회 의무는 확인되지 않았다.** 팀의 필수 활동은 발견된 취약점에 대한 근거 있는 영향·조치 기록이며 필요한 경우 기계 판독 VEX로 제공한다. source/provenance 장부는 실행 데이터의 관측 이력이지 SBOM 또는 VEX가 아니다.

공급망 조치의 게이트는 실제 영향도와 조치 가능성을 고려한다. G1 PDF50(인쇄40)은 CVSS 7.0 이상의 높은 위험도에 즉각적인 완화조치 또는 조치 방안/시기 협의를 요구하며, CVSS 외 KEV 등도 고려하게 한다. 팀은 이를 즉시 영향 평가·조치계획에 연결한다. 인증 우회·민감정보 유출·임의 실행·집행 우회·중복 쓰기를 발생시키는 정탐 또는 알려진 악용 가능 취약점의 노출이 남으면 관련 기능/배포를 차단하고 업데이트·대체·기능 제거 후 재진단한다. 도구 unavailable/scan 실패/영향 미확정은 0개 또는 안전으로 기록하지 않는다. 비적용/예외는 근거·담당자·재검토 기한을 남기며 필수 안전 조건을 예외 승인으로 없애지 않는다.

최종 릴리즈 증거 묶음에는 소스 버전, 정책/fixture 버전·해시, lock·runtime 목록, base 및 제품 image digest, SBOM·검증·SCA/license 결과, 수동 49행/설계20행 결과, REPLAY/LIVE 기록, 수정 전후/재진단표, 설치·운영·패치/rollback 지침을 포함한다. 서명을 적용한 산출물은 실제 서명 검증 증거를 추가한다. 모든 증거에서 실제 token·API키·raw 중요정보를 제거한다.

G1 PDF71~73(인쇄61~63)의 자가점검 30항목도 아래 증거 묶음으로 추적한다. 번호 묶음은 원문 연번이며 짧은 설명은 팀의 산출물 대응이다. 초기 상태는 미점검이다. 선택적 기관/기업 자가점검 양식이라는 원문 맥락과 사용자가 채택한 보안 활동을 구분하고, 대회 공식 제출서식으로 단정하지 않는다.

## 10. 별도 개발 세션 인계와 보고 형식

개발 작업 요청에는 task ID, 읽을 요구/API/원문 페이지, 쓰기 허용 파일, 담당 작성자·검토자, 적용할 G/SR/W ID, 실행 명령, 완료 증거, 실제키/외부 부작용 금지를 포함한다. 공유 계약·DB 전이·작업 장부는 단일 작성자가 통합한다. 새로운 보호 전송/암호저장 등 공통 결정은 관리 세션에서 문서/계약 영향까지 결정한 뒤 해당 범위를 인계한다.

개발 세션 종료 보고는 다음 정보만 사실로 올린다.

- 구현 파일·변경 목적·대상 요구 및 G/SR/W ID.
- 실행한 명령·버전·exit code·실제 시험 PASS/FAIL/NOT_RUN/BLOCKED·evidence 경로.
- 정상 과업 결과, 후보 호출 생성 여부, 판정, executor 진입 및 실제 효과 전후. REPLAY와 LIVE 별도.
- 발견 정탐/오탐·비적용 근거·수정 전후·2차 진단·독립 검토 결과.
- 남은 보호 범위·미해결 공백·다음 작업. 관문 밖의 Codex 내장 셸/파일·모든 IPI·출처 일치의 인과 증명을 확대 주장하지 않음.

계획의 완료는 이 문서를 쓴 것으로 끝나지만, 가이드 준수의 완료는 **확정 적용성·실제 구현·독립 검토·재진단·실행 증거**가 모두 연결된 때에만 판정한다.
