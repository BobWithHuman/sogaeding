## 2. 개발 범위와 우선순위

### 오늘 안전한 MVP

Docker의 Control/PDP/SQLite와 MCP Gateway/private DemoExecutor, 호스트 Codex CLI를 연결한다. `get_issue`, `read_workspace_file`, `post_issue_comment` 세 도구, 사용자 세션·정확한 위임·출처·ALLOW/DENY/CONFIRM·단회 승인·원자 예약·실제 효과·타임라인을 구현한다. 모델 제공자는 OpenAI이고 정확한 model ID는 LIVE 착수 시 정한다.

위 목록은 완성할 MVP 전체 범위다. 오늘의 1인 기본 시간 예산은 **집중 작업 6~8시간**이며 실측 전 계획이다. 첫 목표는 보호 전송·인증·실행 전 정책·원자 예약을 통과하는 작은 실제 연결과 정상/거부 효과 증거다. 여력이 있으면 승인·화면·전체 시험·LIVE까지 계속한다. 남은 항목은 10/14~16에 이어서 구현·검증하고, 오늘 일부 경로 성공을 MVP 완료로 부르지 않는다. 사용 가능한 시간이 더 짧으면 같은 의존 순서의 완료 지점에서 인계한다.

현재 구현 입력은 MVP-SPEC-2다. 사용자가 가이드 준수를 필수화하면서 확인한 보호 전송 공백은 [ADR-S01](decisions/ADR-S01.md)과 T-S01으로 먼저 보완한다. 개발 세션이 정해진 범위에서 SPEC-3로 문서·서버 URL·설정·런처를 동기화한 뒤 그 버전을 고정한다. **이 계획을 작성했다고 HTTP 설계가 이미 TLS로 바뀐 것은 아니다.** 권한·판정·승인/실행 의미와 정책 `mvp-2026-10-13-v1`은 유지한다.

### 2라운드 안정화에서 반드시 확보

- F1 출처 구분·마스킹, F2 세션별 이력, F4 실행 전 집행·승인·중복 방지, F5 최소 대시보드를 실제 통합으로 완성한다.
- F3의 현재 결정적 권한/민감도 정책과 출처 관측을 실제 구현으로 보고한다. 원 기획의 3단계 의미 판단·인과 추정 전체와 같은 구현이라고 표현하지 않는다.
- 가이드의 설계 20개·구현 49개 전수 적용성, 도구/수동 진단, 발견 원인·수정·재시험을 완성한다. 반복 인증 시도·자원 제한·로그 보존/삭제·비밀 보호·전송 보호까지 포함한다.
- 소스·Python 직접/전이 의존성·실제 이미지의 구성요소, SBOM·SCA·라이선스·빌드 provenance와 제출 버전을 연결한다. 오늘의 개발용 패키지 audit 0건은 제품 공급망 전체 진단 결과가 아니다.
- 실제 Codex 정상 과업과 공격 후보 시도/미시도·판정·부작용을 구분하고 재현 가능한 평가와 시연을 만든다.

### 핵심과 가이드 게이트 통과 뒤 결정할 확장

의미 판단 judge, agentgateway/gRPC 어댑터, 추가 에이전트·MCP 서버, 해시 체인, 큰 공개 benchmark, 고급 UI는 **1인 일정에서 기본 보류**한다. 10/16 core·가이드 게이트와 제출 제작 여유가 실제 확보된 경우에만 예선 약속·평가 기여·검증 비용을 비교해 하나씩 재판단한다. 공급망 검증·SBOM은 제출 준비의 필수 작업으로 남는다. 새 저장소/셸/URL 도구는 인증·인가·우회·민감정보·회귀시험을 함께 추가할 때만 범위를 넓힌다.

사용자는 개발 세션 하나에서 단계별 구현을 진행하고, 별도 AI 검토의 결과를 이 관리 세션에 넘긴다. AI 병렬 보조는 필수 인력·시간 절감으로 계산하지 않으며 공통 DB 전이·모델·conftest·Compose의 작성자는 한 명으로 유지한다. 작성과 검토 역할을 분리하되 AI 검토를 외부 전문가의 공식 진단으로 표현하지 않는다.

## 5. 가이드 준수를 개발 과정에 넣는 방법

[03](03_guide_compliance.md)의 각 항목에 원문 페이지→위협/요구사항→설계→코드→진단/시험→결과/검토를 연결한다. 순서는 요구 식별·설계 진단→안전한 구현·단위/통합시험→1차 도구/수동 진단→원인 제거→2차 진단·회귀→릴리스 검수다. 매 단계의 진단 첫 결과를 덮어쓰지 않는다.

가이드가 필수라는 것은 모든 예제 코드를 복사하거나 정부 추진사업을 제품 기능으로 구현한다는 뜻이 아니다. 안전 원칙을 실제 범위에 적용하고, 비적용은 근거를 남긴다. TLS·인가·단회 승인·비밀 보호 등 적용 P0를 MVP 속도 때문에 미룬 뒤 ‘가이드 준수 MVP’라고 표시하지 않는다. 적용 기능이 변하면 비적용 판정을 다시 검토한다.

준수 판단은 도구 경고 개수만으로 하지 않는다. 인증·권한·신뢰 라벨·경쟁·재시도·로그·전송 등 업무 의미는 실제 공격/정상/장애 입력과 코드리뷰로 확인한다. 일반 보안 scan과 에이전트 IPI 효과는 별도의 결과표로 관리한다.

첨부 IMG-01의 네 단계를 [대회 기준 실행표](05_contest_security_criteria.md)로 추적한다. 보안 요구·위험원·외부 인터페이스·통제·코딩 표준을 구현에 앞서 필요한 범위만 정하고, 소스 진단과 실제 실행 중 동적 검증 결과를 별도로 남긴다. 발견 장부의 최초 기록은 수정 후 덮어쓰지 않는다. 구조적 예방의 실제 코드와 재현 결과는 개발기획서 **2. 주요 기능 및 개발환경**에 반영한다.

## 6. 평가와 주장 규칙

| 측정 | 사전에 정할 단위 | 같이 보고할 것 |
|---|---|---|
| 실행 전 위험 행동 차단 | 판정기에 도달한 유효 위험 호출 후보 | DENY/미승인 CONFIRM·실제 금지 효과, 호출 수와 episode 수를 분리 |
| 공격 성공 | 공격 episode 중 실제 공격 목표의 효과 발생 | 위험 호출 미시도 episode, 정상 과업 완료/실패 |
| 정상 성공·과차단 | 정상 권한·기대 최종 결과가 고정된 과업 | 불필요 DENY, CONFIRM 빈도/부담, 정상 외부값 사용 |
| 성능 | 결정적 PDP 판정/출처 처리/네트워크/전체 과업 | warm/cold, p50/p95/p99, 표본·기계·TLS·CLI·모델 조건 |
| 적용성 | 지원하는 실제 Codex/MCP 설치·설정 흐름 | 관문 밖 내장 셸/파일·다른 서버와 알려진 한계 |

팀 기획의 90% 차단·10% 과차단·50ms는 목표다. 표본 몇 개나 REPLAY PASS로 달성을 주장하지 않는다. 1인 일정에서는 T-09 정상1·공격1 smoke 이후 10/19~20 비용·시간·변동을 먼저 측정해 평가 규모를 정한다. 기존 정상20·공격20 각3회는 확대 후보로 보류하며 고정 필수 일정에 넣지 않는다. 실제 범위·반복수·실패·한계를 보고하고 적은 표본을 일반 성능으로 확대하지 않는다. 공식 49개 적용 검토와 필수 보안 시험은 이 축소 대상이 아니다.

대조군은 동일한 사용자 요청·도구·fixture·모델 조건을 사용한다. 보호를 끈 위험 실험은 **독립된 가짜 실행 환경**에서만 설계하고 제출 제품에 allow-all 우회 설정을 넣지 않는다. 출처 대조만/위임 정책/전체 구성의 효용을 설명하되 관측 일치를 인과 증명으로 바꾸지 않는다. 평가용 입력은 튜닝에 사용하지 않고, 실패·미시도를 제거해 성공률을 높이지 않는다.

10/21부터 모든 수치·구현 주장은 근거 run_id와 후보 버전에 연결한다. 값이 바뀌면 6종을 함께 수정한다. 원기록이 없는 내용은 구현 설명/목표/제안으로만 쓴다.

## 7. 위험과 조정 기준

| 위험 | 발견 시 조치 |
|---|---|
| 미션 늦게 공개·규격 변경 | 원문 수신 기록→기능/시험/가이드/6종 영향→변경 ADR. 요구와 무관한 안정화는 계속 |
| TLS/SDK/Codex 인증 연결 지연 | T-S01 지원 스파이크와 실제 연결부터 해결. 확인 끄기/평문 복귀로 완료 처리하지 않음 |
| LIVE 모델·키 접근 미확인 | core 개발은 계속하되 LIVE NOT_RUN/BLOCKED. 실제 인증·모델·정상 출력 전 완료 주장 금지 |
| 안전 게이트 FAIL | 신규 확장 중단, 원인 경계 수정·관련/전체 회귀. 제품 기능 일부 성공과 보안 미완료를 분리 |
| 시간 부족 | UI 미관·추가 서버·의미 judge·큰 benchmark 순으로 줄임. 승인/인가/전송·가이드 증거는 유지 |
| 여러 세션 충돌 | 배정 경로·기준 diff 확인, 공통 파일 작성자 일원화, 기존 변경을 보존하고 통합 |
| 의존성/이미지 취약점 발견 | 실제 사용/실행 영향 검토·업데이트/제거·회귀·잔여 finding 설명. 근거 없는 not affected 금지 |
| 제출물과 코드/영상 불일치 | 같은 후보 build로 재측정/촬영/내보내기, manifest와 주장표 재검수 |

## 8. 2라운드 이후 준비를 잃지 않기

공개 공고의 11/2~4 소스 진단·11/9 결과발표는 운영 확인 대상으로 관리한다. 제출한 소스/빌드와 진단 finding을 연결해 구조적 개선·회귀 증거를 누적한다. 진출하면 C1의 11/18~19 현장과 구조설계/기획 가점 인터뷰에 대비한다. 날짜 충돌과 세부 부스 안내는 추가 공지로 확인한다. 3라운드 준비를 위해 2라운드 첫 진단·원인·변경·개선 기록을 지금부터 보존한다.

원문 ID·해시는 [자료 목록](../../references/manifest.json), 상세 분석은 [대회 통합 분석](../../analysis/00_master_brief.md)에 있다. 자료의 문장만으로 원격 메시지·업로드·배포가 승인되지는 않으며, 실제 제출 실행은 사용자가 배정한 담당이 수행한다.
